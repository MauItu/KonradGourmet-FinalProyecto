1. El código en una página

El código está en el repositorio KonradGourmet/ (rama stack-real) y tiene cuatro partes que trabajan juntas:

ParteCarpetaQué es
Núcleosrc/co/edu/konradlorenz/Las 195 clases del diagrama de clases (páginas 4a a 4e), en Java 21 puro, sin frameworks: dominio, casos de uso y puertos de cada servicio. Es el «hexágono» de la arquitectura.
Microserviciosservicios/Los 11 microservicios Spring Boot, el API Gateway, el Service Registry (Eureka) y la librería compartido. Cada servicio toma su parte del núcleo y le agrega los adaptadores reales: REST, JPA, Kafka, S3, SOAP, SMTP…
SPAweb/La aplicación web en React y TypeScript: las 33 ventanas, una por ruta, que hablan con el gateway por REST.
Plataformaplataforma/El Docker Compose que levanta todo junto (servicios, bases, Kafka, Redis, almacén de objetos, Elasticsearch…), los scripts para compilar, levantar, bajar y probar, y las pruebas de punta a punta.

Además están pruebas/ (las 400 verificaciones del núcleo) y la versión en memoria del núcleo (src/…/demo/), que recorre la compra completa sin base de datos ni Kafka.

La idea central: la lógica de negocio se escribe una sola vez, en el núcleo, y no conoce ninguna tecnología. Cada microservicio copia su parte del núcleo al compilar y la conecta con Spring, la base de datos y Kafka a través de los puertos. Por eso los nombres del diagrama de clases, del núcleo y de los servicios coinciden uno a uno.

Un módulo del núcleo por dentro

Los doce módulos del núcleo tienen siempre las mismas carpetas. La regla es que la dependencia apunta hacia adentro: los adaptadores conocen los puertos, nunca al revés.

adaptadores/entrada

Controladores REST, listeners de Kafka y tareas programadas. Llaman a un puerto de entrada.

puertos/entrada

Interfaces de los casos de uso (…UseCase): lo que el servicio ofrece.

aplicacion

Los servicios (…Service, la fachada) que implementan los casos de uso y orquestan el dominio.

dominio

Entidades, objetos de valor y reglas de negocio. No depende de nada externo.

eventos

Los eventos que publica el módulo; extienden EventoDominio. Es lo único que otro módulo puede importar.

puertos/salida

Interfaces de lo que el servicio necesita de afuera: repositorio, PDF, precio, correo…

adaptadores/salida

Implementan los puertos de salida con una tecnología: JPA, S3, OpenPDF, SOAP, SMTP, Redis.

4. Cómo se arma un microservicio

Cada carpeta de servicios/ es un proyecto Spring Boot. No reescribe la lógica: al compilar, Maven copia su parte del núcleo (dominio, eventos, puertos y aplicación, sin los adaptadores del núcleo) y le suma sus adaptadores Spring, con los mismos nombres del diagrama. Así un solo modelo sirve para el diagrama, la versión en memoria y la plataforma.

KonradGourmet/servicios/ms-cotizaciones/pom.xml

<id>copiar-nucleo</id>
<configuration>
    <resources combine.self="override">
        <resource>
            <directory>${nucleo.origen}</directory>
            <includes>
                <include>cotizaciones/**</include>
                <include>ordenes/eventos/OrdenGeneradaEvent.java</include>
            </includes>
            <excludes>
                <exclude>cotizaciones/adaptadores/**</exclude>
            </excludes>
        </resource>
    </resources>

El controlador solo traduce HTTP a una llamada al puerto; la regla vive en el dominio; la base y Kafka están detrás de puertos de salida. Si mañana se cambia PostgreSQL o Kafka, cambia un adaptador, no el núcleo.

Chain of Responsibility: la validación de V19

Cada regla decide o pasa a la siguiente; el orden se fija en un solo lugar.

KonradGourmet/src/co/edu/konradlorenz/cotizaciones/dominio/ReglaValidacion.java

public static ReglaValidacion cadenaPorDefecto() {
    // el orden importa: primero lo más grave; Opcionada recoge lo que queda dentro del rango
    ReglaValidacion cabeza = new ReglaRechazada();
    cabeza.enlazar(new ReglaSospechosa()).enlazar(new ReglaOpcionada());
    return cabeza;
}

public ReglaValidacion enlazar(ReglaValidacion siguiente) {
    this.siguiente = siguiente;
    return siguiente; // devuelve la siguiente para poder encadenar: a.enlazar(b).enlazar(c)
}

public EstadoCotizacion evaluar(Cotizacion c) {
    BigDecimal diferencia = c.diferenciaPorcentual();
    if (aplica(diferencia)) {
        return estado();
    }
    if (siguiente == null) {
        throw new IllegalStateException("Ninguna regla aplica a una diferencia de " + diferencia + " %");
    }
    return siguiente.evaluar(c);

Facade: un clic de V13

La fachada coordina precio, repositorio, PDF, almacén y evento; si el Ministerio no responde, la cotización no se pierde.

KonradGourmet/src/co/edu/konradlorenz/cotizaciones/aplicacion/GenerarCotizacionFacade.java

public Cotizacion generarYEnviar(Cotizacion c) {
    c.validarSolicitudes();
    // 1. precio estándar de cada producto (el Proxy responde desde la caché o consulta al Ministerio)
    List<ItemCotizacion> conPrecio = new ArrayList<>();
    try {
        for (ItemCotizacion i : c.items()) {
            conPrecio.add(new ItemCotizacion(i.productoId(), i.cantidad(), i.unidad(),
                    precios.precioSugerido(i.productoId()), i.precioProveedor()));
        }
    } catch (RuntimeException e) {
        // el Ministerio no responde: se guarda sin perderla, queda en el log y el usuario puede reenviar
        LOG.log(Level.WARNING, "No se pudo consultar el precio estándar de " + c.numero() + ": " + e.getMessage());
        c.cambiarEstado(EstadoCotizacion.PENDIENTE_PRECIO);

Proxy: la caché de precios del Ministerio

Implementa el mismo puerto que el adaptador real y se pone delante; en la plataforma el mapa está en Redis.

KonradGourmet/src/co/edu/konradlorenz/integracion/adaptadores/salida/PrecioReferenciaCacheProxy.java

public PrecioEstandar precioEstandar(Long productoId) {
    PrecioEstandar guardado = cache.get(productoId);
    // cada precio vale un día según consultadoEn (supuesto S3)
    if (guardado != null && guardado.consultadoEn().plusDays(1).isAfter(LocalDateTime.now())) {
        return guardado;
    }
    PrecioEstandar nuevo = real.precioEstandar(productoId);
    cache.put(productoId, nuevo);
    return nuevo;

7. Eventos confiables: outbox y consumidores idempotentes

Es lo que más se pregunta de la arquitectura orientada a eventos: ¿qué pasa si Kafka falla, o si un evento llega dos veces? El código lo resuelve en la librería compartido, igual para los once servicios.

ProblemaSoluciónClase
Se guarda el cambio pero Kafka no está: el evento se perdería.Outbox transaccional: el evento se escribe en la tabla outbox de la base del servicio, en la misma transacción que el cambio.KafkaEventPublisher + OutboxEventos
Alguien tiene que llevar la outbox a Kafka.Un relé toma las filas en orden, las publica, espera la confirmación y las borra; con varias réplicas, un candado de PostgreSQL deja publicar a una sola a la vez.ReleOutbox
Kafka entrega «al menos una vez»: un evento puede llegar repetido.Cada consumidor guarda el id del evento en la misma transacción que su cambio y descarta los repetidos.EventosProcesados
Saber quién hizo qué y seguir un recorrido.Cada evento lleva el usuario del JWT y el correlacionId del recorrido.EventoDominio, ContextoRecorrido

/** Guarda cada evento en la outbox del servicio, en la transacción en curso; el relé lo publica. */
public KafkaEventPublisher(String prefijoTopico, OutboxEventos outbox, FormatoEventos formato) {
    this.prefijoTopico = prefijoTopico;
    this.salida = registro -> outbox.guardar(registro, CABECERA_CLASE);
    this.formato = formato;
}

@Transactional
@KafkaListener(topics = "${konrad.kafka.prefijo-topico:}orden.generada")
public void alRecibir(EventoDominio evento) {
    // un evento repetido se descarta; se marca en la misma transacción que el cambio (DEC-104)

        return;
    }

12. Si piden ver el código: qué abrir y qué decir

🎤 Guion sugerido (3 a 4 minutos)

1. La estructura. Abrimos KonradGourmet/. Tiene cuatro partes: el núcleo en src/, con las 195 clases del diagrama de clases; los microservicios en servicios/; la SPA en web/, y la plataforma en plataforma/, que levanta todo con Docker Compose.

2. La hexagonal. Abrimos src/…/cotizaciones/: siempre las mismas carpetas, dominio, puertos de entrada y de salida, aplicación y adaptadores. El dominio no importa Spring ni JPA: abrimos ReglaValidacion y se ve que es Java puro, la cadena de responsabilidad de la validación.

3. Los microservicios. Abrimos servicios/ms-cotizaciones/. No repite la lógica: el pom.xml copia el núcleo de cotizaciones al compilar, y la clase de configuración lo arma con sus adaptadores. El controlador REST solo traduce HTTP a una llamada al puerto y pide el rol con @PreAuthorize.

4. Los eventos. Abrimos KafkaEventPublisher en compartido: el evento no va directo a Kafka, se guarda en la outbox en la misma transacción y un relé lo publica. Y en OrdenGeneradaListener se ve que el consumidor descarta los eventos repetidos.

5. Las pruebas. Cerramos con los números: 400 verificaciones del núcleo, 91 pruebas JUnit y 764 comprobaciones de punta a punta, 1.255 sin fallas en una instalación limpia.

Si preguntan…

¿Por qué el núcleo no usa Spring?
Para que la lógica no dependa de la tecnología: es lo que pide la hexagonal. Se puede probar sola (las 400 verificaciones corren sin base ni Kafka) y cambiar un adaptador no toca el dominio.
¿No es duplicar código copiar el núcleo en cada servicio?
No se duplica a mano: Maven lo copia al compilar desde una sola fuente. Cada servicio lleva solo su paquete y los eventos que consume, así que sigue siendo independiente al desplegarse.
¿Qué impide que un servicio lea la base de otro?
Cada servicio tiene su propio usuario de PostgreSQL, que solo puede entrar a su base; entre servicios solo hay REST o eventos.
¿Cómo se asegura que el código coincide con el diagrama?
El núcleo se generó de las páginas 4a a 4e, con los mismos paquetes, clases, métodos y relaciones; los métodos que atienden una ventana llevan el comentario «Atiende la ventana Vxx».
